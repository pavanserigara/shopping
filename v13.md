# Upgrade prompt (v12) — Local Shop OS: delivery address at checkout + recommended additions

Paste this into Antigravity as a follow-up brief, after v1–v11 are built. This pass fixes a real gap — there's currently no way for a customer to provide a delivery address when ordering — plus adds a set of smaller features that genuinely help both shop owners and customers use the platform day to day.

---

## Fix: Add delivery address to the checkout flow

Right now a customer can add items to cart and send the order via WhatsApp, but there's no structured place to capture where the order should be delivered — this is a real gap for any shop actually fulfilling delivery orders.

- Add an **address step** to the cart/checkout flow, before the "Order via WhatsApp" action:
  - **Pickup or Delivery toggle** — let the customer choose, but only show this toggle if the shop has delivery enabled (see the "Delivery available" setting below). If a shop has delivery turned off, checkout goes straight to pickup with no toggle shown at all. If "Pickup," skip the address form entirely. If "Delivery," show the address fields.
  - Address fields: full address (textarea, so it can include flat/house number, street, landmark), and a separate contact phone number field (pre-filled if already captured elsewhere in the session).
  - Optional: an "Use my current location" button using browser geolocation to auto-fill a rough address/pin — purely a convenience, must still allow manual entry/editing since geolocation on mobile browsers isn't always precise for a full address.
- Include the address (and pickup/delivery choice) in:
  - The `orders` table — add `delivery_type` ('pickup'/'delivery'), `delivery_address`, `delivery_contact` columns.
  - The WhatsApp pre-filled message — the shop owner should see the full delivery address directly in the WhatsApp order text, not have to ask for it separately.
  - The tenant's order inbox — address should be visible on each order without needing to click into a separate detail view for delivery orders.
- **Save the last-used address for repeat customers**: since there's no login, store the last address in browser local state (session/local storage) scoped per shop, so a returning customer on the same device doesn't have to retype it every time — always let them edit it, don't just silently reuse it without showing it first.
- Validate that an address is filled in before allowing a "Delivery" order to be submitted (basic required-field check) — but keep the form short, this is a small local shop order, not a full checkout wizard.

## Recommended extra features

These are worth adding because they directly support real usage patterns for small shops and their customers — prioritized roughly by how much they matter day to day.

### 1. Delivery settings per shop (tenant dashboard)
- Add a master **"Delivery available" on/off toggle** for the shop, in the tenant dashboard settings. This is the primary control:
  - **If OFF**: the storefront checkout only shows "Pickup" — the delivery option and address form are hidden entirely, not just disabled/grayed out.
  - **If ON**: the storefront checkout shows the Pickup/Delivery toggle from the fix above, and the delivery settings below become available.
- When delivery is ON, let a tenant optionally set: a flat delivery fee (or "free delivery"), a minimum order amount for delivery, and a rough delivery area/radius description (free text, e.g. "within 3km of the shop" — no need for real geofencing yet).
- If set, show these clearly on the storefront near the pickup/delivery toggle, and include the delivery fee in the order total.
- Store this as a `delivery_enabled` boolean column on `tenants`, checked before rendering the delivery UI on the storefront at all — this should be enforced server-side too (reject a delivery order for a shop with `delivery_enabled = false`), not just hidden in the UI.

### 2. Payment mode selection at checkout (informational only, no gateway needed)
- Add a simple choice at checkout: "Cash on Delivery" or "UPI/Pay at pickup" — this doesn't process any payment, it just tells the shop owner what to expect, included in the WhatsApp message and order record. Genuinely useful for shop owners planning their day, and easy to build since no payment integration is involved.

### 3. Order confirmation auto-message customization
- Let a tenant customize a short thank-you/confirmation line that appears to the customer after placing an order (e.g. "Thanks for ordering from Laxmi Kirana! We'll confirm on WhatsApp shortly.") — small touch, but makes each shop feel like its own branded experience rather than a generic platform message.

### 4. Best-selling products (tenant dashboard insight)
- On the sales report/dashboard overview, show a simple "top 5 products this month" list computed from `order_items` — helps a shop owner know what to restock and what to feature/promote, using data you're already collecting.

### 5. Repeat customer recognition (lightweight, no login)
- If a customer's phone number/contact matches a previous order for that shop, show a small "Welcome back!" note during checkout — a nice touch that costs little to build since you already store `customer_contact` on orders, and helps the shop feel more personal.

### 6. Minimum order handling
- If a tenant sets a delivery minimum (from #1) and the cart total is below it, show a clear inline message ("Add ₹X more for delivery, or switch to pickup") rather than only blocking at the final submit step — reduces checkout frustration.

## What NOT to change in this pass
- Don't touch the plan/feature-gating logic, multi-tenancy model, or the landing page — this pass is checkout/order flow and a few small dashboard additions only.
- Don't add real payment gateway integration — payment mode selection here is informational, not a transaction.

## Deliverable
