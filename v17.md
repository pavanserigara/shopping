## Step 1: Remove the existing implementation
- Delete the current settings form, its save endpoint, and any related JS — start this module clean rather than patching on top of whatever is currently broken.

## Step 2: Rebuild the database layer
Confirm/enforce `platform_settings` as a genuine single-row config table:

```sql
platform_settings
  id INT PRIMARY KEY (always 1 — enforced, never a second row)
  support_contact_number VARCHAR(20)
  site_name VARCHAR(100)
  site_logo_url VARCHAR(255)
  primary_color VARCHAR(7)
  accent_color VARCHAR(7)
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

- On first app setup, insert exactly one row with `id = 1` and sensible defaults if it doesn't already exist. Every save must be an `UPDATE ... WHERE id = 1` — never an `INSERT`.

## Step 3: Rebuild the backend endpoint
- One clear endpoint, e.g. `POST /admin/settings/update`, that:
  - Confirms the requester is an authenticated super admin.
  - Validates each field server-side (phone number format, hex color format for the color fields, logo file type/size if a new logo is uploaded).
  - Runs a single `UPDATE platform_settings SET ... WHERE id = 1` covering all fields submitted together.
  - Returns clear JSON: `{success: true, data: {...updated values...}}` on success, or `{success: false, message: "..."}` on failure — never a raw error page or empty body.

## Step 4: Rebuild the frontend form
- A single settings form covering all fields (support number, site name, logo upload, primary color picker, accent color picker), submitted via `fetch`/AJAX.
- On success: show a success toast immediately, and update the fields on screen to reflect the confirmed saved values from the response (don't just assume the input's current value is correct — reflect what the server actually confirmed was saved).
- On failure: show the actual error message returned, not a generic "something went wrong."
- No page reload required at any point in this flow.
