# Upgrade prompt (v17) — Local Shop OS: performance optimization for shared hosting

Paste this into Antigravity as a follow-up brief. This pass is a performance/optimization pass, not new features — the app is deployed on Hostinger Premium shared hosting, which has a limited concurrent MySQL connection cap (shared hosting typically limits this to around 20-25 simultaneous connections per database). Optimize the app to use connections efficiently, add caching for frequently-read data, and generally tighten performance for a shared-hosting environment.

---

## Part A: Database connection handling

- **Never use persistent connections** (`PDO::ATTR_PERSISTENT`) — on shared hosting with a low connection cap, persistent connections stay open and can exhaust the limit fast under even light concurrent traffic. Use standard short-lived PDO connections instead.
- **Open the connection as late as possible, close it as early as possible** within each request — don't open a DB connection at the top of a shared bootstrap/config file if a given page doesn't need it immediately; connect right before the first query that needs it.
- **Explicitly unset/null the PDO connection object** once all queries in a request are done, rather than relying only on PHP's end-of-script cleanup — this matters more on long-running admin pages that might do several sequential operations.
- **Audit for connection leaks**: check every file that opens its own PDO connection rather than reusing a single shared connection instance per request — if multiple files/functions each open their own connection during a single page load, consolidate to one connection per request, passed to whatever needs it, rather than opening several.
- **Use a single shared database connection helper/class** (a simple singleton-style connection function is fine, doesn't need to be an elaborate pattern) so every part of the app reuses one connection per request instead of each feature independently connecting.
- **Add basic retry/graceful failure handling**: if a connection attempt fails (e.g. because the concurrent limit was briefly hit), catch it and show a clear "please try again in a moment" message instead of a raw PHP/database error — this protects against the exact failure mode this connection cap creates under load.

## Part B: Add caching for frequently-read, rarely-changed data

Several pieces of data are read on nearly every request but change rarely — cache these instead of querying the database every time.

- **What to cache**: `platform_settings` (read on almost every page load for branding/support number), the `plans` + `plan_features` data (read on the landing page pricing section and every plan-gating check), and each tenant's basic info (`tenants` row — name, subdomain, logo, delivery settings) since it's read on every storefront page view for that shop.
- **Caching approach for shared hosting**: since Hostinger shared hosting typically doesn't provide Redis/Memcached, use **file-based caching** — write the cached data as a JSON file (e.g. in a `/cache` directory not publicly web-accessible) with a short TTL (e.g. 5-10 minutes for tenant/settings data), or use **PHP's OPcache/APCu if available on the plan** (check what's enabled in hPanel) for in-memory caching within a single server process.
- **Cache invalidation**: whenever platform settings, a plan, or a tenant's info is updated via the admin panels (per the AJAX save flows already built), delete/refresh the corresponding cache file immediately as part of that save — never let a save succeed while stale cached data keeps showing elsewhere. This is important: getting cache invalidation wrong causes exactly the kind of "I saved it but it's not showing" bug already fixed in earlier passes — don't reintroduce that bug via caching.
- Do **not** cache anything that changes frequently or must always be fresh: order data, order status, cart contents, ad view counts, stock counts. These must always hit the database directly.

## Part C: Query and index optimization

- Add database indexes on columns used heavily in `WHERE`/`JOIN`/`ORDER BY` clauses that don't already have them — at minimum: `tenant_id` on every tenant-scoped table (products, orders, coupons, ads), `subdomain` on `tenants` (this is looked up on every storefront page view), `status` and `created_at` on `orders` (used for the order list filters from v7), and `expires_at`/`is_active` on `coupons`.
- Audit for **N+1 query patterns** — e.g. loading a list of orders and then running a separate query per order to get its items, instead of a single join or a single batched query. Fix any of these found in the order list, product list, or plan feature-checklist rendering.
- Make sure paginated lists (orders, tenant list in super admin) actually use `LIMIT`/`OFFSET` at the database level, not "fetch everything, then slice in PHP" — the latter wastes both connection time and memory.

## Part D: General shared-hosting performance hygiene

- Enable **gzip compression** and **browser caching headers** for static assets (CSS, JS, images) via `.htaccess` — reduces repeated load on the server for returning visitors.
- Confirm **image uploads are compressed/resized server-side** on upload (product photos, ad banners, logos) rather than storing full-resolution originals and shrinking them client-side only — this reduces both storage use and page load time, and matters more now that connection/resource limits are a real constraint.
- Confirm lazy-loading of below-the-fold images (from earlier storefront passes) is actually working — verify with browser dev tools, don't assume it's still working after later passes touched the same pages.
- Minify CSS/JS for production if not already done.

## Testing this pass
- Simulate multiple simultaneous requests (even just opening the storefront in several browser tabs/devices at once) and confirm no "too many connections" errors occur under light concurrent load.
- Confirm changing a platform setting, a plan, or a tenant's info is reflected correctly and immediately everywhere, even with caching now in place — re-run the settings test script from v16 and the plan-display check from v7 to confirm caching didn't reintroduce either bug.
- Check page load times before and after this pass on a few key pages (storefront, landing page) to confirm the optimization work had a measurable effect.

## What NOT to change in this pass
- Don't add new features or change the visual design — this pass is purely backend/performance optimization.

## Deliverable
Reduced and properly managed database connection usage (no persistent connections, no connection leaks, graceful handling if the connection limit is briefly hit), a working file-based (or APCu, if available) cache layer for platform settings, plans, and tenant info with correct invalidation on save, added indexes on the key lookup columns, fixed N+1 query patterns, and general static-asset performance hygiene — with a `README.md` note listing what was cached, the TTLs used, and confirmation that the settings/plan live-update tests still pass with caching in place.
