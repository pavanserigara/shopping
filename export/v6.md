# Upgrade prompt (v6) — Local Shop OS: plans, feature gating, and platform-wide ads

Paste this into Antigravity as a follow-up brief, after v1–v5 are built. This is the biggest structural addition so far: a proper plan/subscription system with per-feature access control, plus platform-wide ads run directly by the super admin. Keep the yellow/white theme, logo, and everything built in v1–v5 — this pass adds a permission layer on top, it doesn't redesign anything.

---

## Part A: Plan system (Free / Premium / Gold, and custom plans)

### A1. Plans are admin-defined, not hardcoded
The super admin must be able to create, edit, and delete plans from the super admin panel — don't hardcode "Free/Premium/Gold" as fixed code paths. Build a generic plan system where those are just the first three plans created through the UI.

New table:
```sql
plans
  id, name, price, billing_period (e.g. 'monthly'), product_limit, is_default, created_at
```

- Super admin can click "Create new plan," enter a name (e.g. "Gold"), a price, and a product limit for that plan (reuses the `product_limit` concept from v5, now scoped per plan instead of per tenant).
- One plan should be markable as `is_default` — this is the plan a shop falls onto automatically after their trial ends, if they haven't purchased a paid plan (typically the Free plan).

### A2. Feature list and plan-feature mapping
Every feature that exists in the tenant dashboard must be represented as a discrete, checkable feature the super admin can assign to a plan.

New table:
```sql
plan_features
  id, plan_id, feature_key
```

Build a feature registry covering every tenant-facing capability shipped so far, at minimum:
- `product_management` — add/edit/delete products
- `product_image_gallery` — multiple images per product (v2)
- `order_management` — order inbox, status updates (v1/v2)
- `sales_reports` — sales report view (v1)
- `shop_ads` — tenant-managed banner/mid-page ads (v2/v5)
- `ad_analytics` — ad view-count analytics (v5)
- `shop_logo_upload` — logo upload (v5)
- `shop_directory_listing` — visibility in the public `/shops` directory (v2/v5)
- Add any other tenant-dashboard feature that exists in the current build to this list — the goal is that **nothing in the tenant dashboard is ungated**, every section maps to a `feature_key`.

### A3. Plan builder UI (super admin)
When creating or editing a plan, show a checklist (checkboxes) of every feature key above. The super admin ticks which features are included in that plan and saves. This is what determines what a tenant with that plan can access.

### A4. Assigning a plan to a tenant
- Add `plan_id` to the `tenants` table.
- Super admin can assign/change a tenant's plan from the tenant list/detail view in the super admin panel (in addition to the existing suspend/reactivate control from v1).
- New signups are assigned no paid plan initially — they're on **trial**, and during trial they get full access to all features regardless of plan (see A5), not restricted to the default plan's feature set.

### A5. Trial behavior
- During the trial window (`trial_ends_at`, from v5), the tenant has access to **every feature**, regardless of plan — this is the whole trial pitch, let them experience the full product.
- Once the trial ends, the tenant drops to whatever plan they're on (`plan_id`) — if they haven't purchased anything, that's the `is_default` plan (typically Free, with a limited feature set and lower product limit).

## Part B: Feature gating in the tenant dashboard

For every feature in the registry (A2), the tenant dashboard must check: is this tenant currently in trial (full access), or does their current plan include this `feature_key`?

- **If allowed**: show the feature normally, fully functional.
- **If not allowed**: show the feature's nav entry/section, but in a **locked state** — grayed out or with a lock icon overlay, and clicking it shows a clear message: *"This feature isn't included in your current plan. Please purchase a higher plan to unlock [feature name]."* with a button linking to a plan-comparison/upgrade page.
- Do this consistently across every gated feature (ads, image gallery, analytics, logo upload, etc.) — same lock pattern, same messaging style, reused as one shared UI component rather than rebuilt per feature.
- Build a simple **plan comparison page** (tenant-facing) showing each plan, its price, and which features are included (reuse the same feature registry to render a comparison table) — this is what the "upgrade" links point to.

## Part C: Platform-wide ads (super admin)

Currently ads (v2/v5) are managed per-tenant and shown only on that tenant's storefront. Add a second, separate ad system that the **super admin** controls directly, shown across **every** shop's storefront platform-wide.

New table:
```sql
global_ads
  id, image_url, link_url, placement ('banner' or 'mid_page'), active, start_date, end_date, created_at
```

- Super admin gets an "Ads" section in the super admin panel (same upload/preview/schedule/activate pattern already built for tenant ads in v2/v5 — reuse that UI pattern, don't rebuild it from scratch).
- Global ads render on **every** shop's storefront, in the same banner/mid-page placements as tenant ads — decide a clear rule for how they combine (e.g. global ads always show first in the banner carousel, tenant ads follow; or global ads take the mid-page slot while tenant ads take the top banner — pick one clear rule and apply it consistently everywhere).
- Track view counts for global ads the same way as tenant ad analytics from v5 (`global_ad_id, viewed_at`), and show the view count to the super admin in the same panel.
- This is the platform's own monetization/promotion channel — separate and independent from what individual shop owners upload for their own shop.

## What NOT to change in this pass
- Don't touch the WhatsApp ordering flow, product/order schema, or the yellow/white visual theme.
- Don't remove or restrict any feature for tenants currently in trial — trial must always mean full access, this is non-negotiable for the pitch to work.

## Deliverable
A working plan system (create/edit plans with a feature checklist, assign plans to tenants), consistent feature-gating with a locked-state UI and upgrade prompt across every gated tenant feature, a tenant-facing plan comparison page, a platform-wide ad system controlled by the super admin and shown across all storefronts with its own view analytics, and a short note in `README.md` listing new tables (`plans`, `plan_features`, `global_ads`, `global_ad_views` or similar) and the full feature-key registry used for gating.
