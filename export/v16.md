# Upgrade prompt (v15) — Local Shop OS: fix platform settings not saving

Paste this into Antigravity as a follow-up brief. The super admin **Settings** section (support contact number, site name, logo, theme colors — from earlier passes) is not actually saving changes — specifically, updating the support contact number has no effect. Diagnose the real cause first, then fix it properly across the whole settings save flow, not just the phone number field.

---

## Step 0: Diagnose before fixing
- Open the browser console/network tab while changing the support contact number and clicking save — capture the actual request being sent (is it firing at all? what's in the request body?) and the actual response (status code, response body).
- Check the server-side log for the corresponding request.
- Confirm directly in the database whether the `platform_settings` row is actually being updated when save is clicked, or not touched at all — query it before and after clicking save.
- State plainly what the actual root cause is before fixing — likely candidates to check specifically:
  - The save button/form isn't wired to an endpoint at all (a leftover static form from before the settings feature was made dynamic).
  - The endpoint exists but is reading the wrong field name from the request (a mismatch between the form's input `name` attribute and what the backend expects).
  - The update query is running but targeting the wrong row (e.g. inserting a new `platform_settings` row each time instead of updating the single existing one, so the app is still reading the old row).
  - The value is saving correctly to the database, but the page that displays the support number elsewhere (footer, landing page, tenant dashboard) is still reading a hardcoded value instead of pulling from `platform_settings` — meaning the save works but appears broken because it's invisible everywhere it should show.

## Step 1: Fix the save flow properly
- Confirm `platform_settings` is a genuine single-row config table — enforce that updates always target that one existing row (`UPDATE ... WHERE id = 1` or equivalent), never inserting a duplicate row.
- Fix the save endpoint to correctly read and persist every settings field on this page (not just the phone number — check site name, logo, and theme colors from the same section too, since they may share the same broken save path).
- Return a proper JSON success/error response, and confirm the save button shows a success toast immediately (per the v13 fix) with no manual refresh needed to see the change reflected on the settings page itself.

## Step 2: Fix every place that should display these settings but doesn't
Once saving genuinely works, audit every place across the platform that is supposed to read from `platform_settings` and confirm each one is actually pulling live data, not a hardcoded value:
- Support contact number: landing page footer, tenant dashboard help/support area, any other "contact us" reference.
- Site name: landing page header/title tag, storefront "Powered by" credit footer, browser tab title.
- Site logo: landing page header, favicon, storefront credit footer.
- Theme colors: confirm changing these actually updates the CSS variables platform-wide, not just on the settings page preview (if a live preview exists).

## Step 3: Test end to end before calling this done
1. As super admin, change the support contact number to a clearly different test value and save.
2. Confirm a success toast appears immediately, with no refresh.
3. Refresh the settings page anyway and confirm the new value is still there (proves it actually persisted, not just updated the UI optimistically without saving).
4. Visit the landing page footer and confirm the new number appears there.
5. Visit a tenant dashboard's support/help area and confirm it shows the same new number.
6. Repeat the same save-and-verify check for site name and logo.
